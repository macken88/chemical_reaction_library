1. 目的・基本方針

本アプリは、化学反応を構造式として編集・確認し、決定論的なルールに基づくValidationを実施したうえで、実務上のメモとともに反応ライブラリへ保存・再利用することを目的とする。

基本原則：アプリは「その反応が現実に起こること」を保証しない。構造表現、元素・電荷収支、原子価、atom mapping等の機械的に評価可能な整合性を検証し、最終的な登録判断はユーザーが行う。
  • 入力経路は Editor と Import の2つに限定する。
  • どちらの入力も共通の Reaction Draft に変換し、登録直前に必ず共通Validationを通す。
  • Validation結果にWarningがあっても、保存可能な構造であればユーザー判断で登録できる。
  • ポリマー等、完全な分子として表現できない反応を排除しない。
  • 外部AIはアプリ内に組み込まず、テキストコピー／Importを通じて疎結合に連携する。
  • 個人利用を前提とし、配布・インストーラ最適化よりも実装の自然さと拡張性を優先する。

2. 初版の対象範囲

2.1 対象反応

  • 低分子の通常化学反応
  • 単純なホモポリマー
  • 単一の記号 n で表現可能な重合・繰返し構造
  • 架橋反応等、生成物全体を有限分子として完全表現できないが、局所構造として記録可能な反応
  • 反応物、生成物に加え、触媒・溶媒・添加剤等の反応条件側成分を含む反応

2.2 初版では対象外

  • 複雑な共重合体、分岐ポリマー、統計的ポリマー組成の完全表現
  • 複数の独立変数 x, y 等を用いる一般的な代数化学量論
  • BigSMILES等の高度なポリマー専用表記
  • AIによる自動化学妥当性判定
  • 登録履歴・版管理

4. 全体ユーザーフロー

┌──────────────┐ │ New Reaction │ └──────┬───────┘ │ ┌──────────┴──────────┐ ▼ ▼ Editor Import │ │ │ Parse / Convert │ │ └─────────┬───────────┘ ▼ Reaction Draft │ 編集・メモ・タグ追加 │ ▼ Validation │ ┌────────┴────────┐ ▼ ▼ 修正に戻る 登録する │ ▼ Library

4.1 共通原則

  • EditorとImportで別々のValidation実装を持たない。
  • Import後のデータもEditorで確認・修正できる。
  • Validation画面は登録可否を自動決定せず、ユーザーへ判断材料を提示する。
  • 保存済み反応の再編集時も、保存直前にValidationを再実行する。

5. Editor仕様

5.1 構造編集

  • Ketcher上で反応物・生成物を構造式として描画・編集できる。
  • 触媒・溶媒・添加剤等を「反応条件側成分」として登録できる。
  • 各成分は以下のいずれかの役割を持つ。
    • Reactant（反応物）
    • Product（生成物）
    • Condition component（触媒・溶媒・添加剤等）
  • Condition componentは元素収支・電荷収支の対象外とする。
  • 化学量論係数はユーザーが入力可能とする。
  • 通常の数値係数と、初版では単一の n を扱える。

5.2 付帯情報

反応構造とは別に以下を入力できる。

  • 反応名（任意）
  • タグ（複数）
  • 試薬・触媒等に関する自由記述
  • 加工工程・条件に関する自由記述
  • 一般自由記述メモ
  • Validation Warningを許容して登録する理由（任意）

市販試薬、メーカー、温度、時間、圧力等は初版では専用フィールドへ正規化せず、自由記述で扱う。

6. Import仕様

6.1 対応形式

  • Reaction SMILES
  • RXN file

6.2 Importフロー

外部テキスト / RXN │ ▼ 形式判定・Parse │ ├─ 成功 → Reaction Draft生成 │ │ │ ▼ │ Editorでプレビュー・修正 │ │ │ ▼ │ Validation │ └─ 失敗 → エラー内容表示 │ └─ 原文を保持して修正可能

6.3 Importの責務

Importは「登録機能」ではなく、外部表現をアプリ内部のReaction Draftへ変換する入力機能とする。Import直後の自動登録は禁止する。

7. Validation仕様

7.1 Validationの役割

Validationは、入力された反応のうちアプリが機械的に確認できる範囲を検証し、結果と検証範囲をユーザーへ提示する。

7.2 自動Validationモード

ユーザーには反応タイプを選択させず、構造表現から自動判定する。

内部モード対象主な検証範囲
FULL 全成分を有限の完全構造として扱える反応 構造、原子価、元素収支、電荷収支、atom mapping、結合変化
REPEAT_UNIT 単純ホモポリマー、SRU等の繰返し構造 繰返し単位、接続点、局所原子価、単一nを考慮した単位収支
LOCAL 架橋等、全体ネットワークを有限分子で表せない反応 描画された局所構造、反応部位、結合生成・切断、局所原子価
LIMITED 曖昧・不完全表現を含み、十分な構造検証ができない場合 保存可能性、取得できる最小限の構造情報。評価不能項目を明示

7.3 自動分類の基本ロジック

if complete_finite_structures_without_undefined_features:
    mode = FULL
elif contains_supported_repeat_unit:
    mode = REPEAT_UNIT
elif valid_local_structure_is_available:
    mode = LOCAL
else:
    mode = LIMITED
注意：RDKitでparseできたことだけをFULL判定条件にしない。dummy atom、未定義結合、polymer S-group等の有無を追加確認する。

7.4 共通Validation項目

項目内容状態
Representationアプリ内部形式として保存・再表示可能かPass / Fail
Structure構造・結合・原子価等の整合性Pass / Warning / Fail / Not evaluable
Element balance反応物・生成物の元素数比較Pass / Warning / Not evaluable
Charge balance総formal chargeの比較Pass / Warning / Not evaluable
Atom mappingmappingの不足・不整合Pass / Warning / Not evaluable
Bond changes生成・切断・結合次数変化の抽出Info / Warning / Not evaluable

7.5 元素収支

  • ReactantとProductのみ対象とし、Condition componentは除外する。
  • 元素ごとの個数と差分を明示する。
  • 単なるOK/NGだけでなく、例：「Product側でHが2不足」を表示する。
  • 数値係数を反映する。
  • REPEAT_UNITでは初版に限り単一の n を記号的に扱う。
  • 全体収支を一意に評価できない場合はFailではなく Not evaluable とする。

7.6 重大度

  • Error：保存・再利用に必要な構造表現そのものが成立しない等。
  • Warning：元素収支不一致、電荷不一致、mapping不足等。ユーザー判断で登録可。
  • Info：評価対象外、未指定、結合変化等の補足。

7.7 登録判断

  • Validation後に「修正へ戻る」「この内容で登録」を提示する。
  • Warningを残したまま登録可能。
  • Warning理由欄は表示するが入力必須としない。
  • Validationモードの手動変更は初版では提供しない。

8. ポリマー対応

8.1 初版の対象

単純ホモポリマーを対象とし、SRU等の繰返し単位をアプリ上で保持・描画できることを要求する。

8.2 化学量論

初版で記号係数として扱うのは単一の n のみとする。

例： n A → [A]n または、繰返し単位ベースで A ↔ repeat unit の元素関係を評価する。

8.3 架橋等

全ポリマーネットワークを1つの完全な分子として構築することを要求しない。LOCALモードにより、反応部位の局所構造と結合変化を検証する。

8.4 表現可能性と検証可能性の分離

  • 構造を保存・再描画できること：登録上の基本要件
  • RDKitで完全解釈できること：Validation能力を高める条件
  • 元素収支を計算できること：可能な場合のみ実施

9. 登録・編集・削除

9.1 新規登録

  • EditorまたはImportからReaction Draftを作る。
  • 登録直前にValidationを必ず実行する。
  • 結果確認後、ユーザーが登録を確定する。

9.2 重複警告

  • 初版ではReaction SMILESの完全一致のみ検出する。
  • 完全一致が見つかった場合はWarningを出すが、登録自体は禁止しない。

9.3 編集

  • 保存済み反応をEditorへ読み込み、構造・メモ・タグ等を編集できる。
  • 更新保存の直前にValidationを再実行する。
  • 初版では改訂履歴を保持しない。

9.4 削除

  • 登録済み反応を削除可能とする。
  • 誤操作防止の確認ダイアログを表示する。
  • 初版では履歴保持を要求しないため、確定後はDBから削除してよい。

9.5 再Validation

  • 個別反応を再Validationできる。
  • Library全体を一括再Validationできる。
  • ValidationロジックやRDKit更新後に再評価できる設計とする。
  • 最新Validation結果と実行日時を保存する。

10. Library・検索

10.1 一覧

保存済み反応について、最低限以下を表示する。

  • 反応名
  • 構造式プレビュー
  • 主要タグ
  • Validation coverage / 状態
  • Warning有無
  • 更新日時

10.2 検索条件

  • 試薬名
  • タグ
  • 自由記述全文
  • Reactantに特定分子が含まれる
  • Productに特定分子が含まれる
  • Validation状態

10.3 構造部分検索

初版に含める。ただしユーザーへ生のSMARTS入力を要求せず、Ketcher等で検索部分構造を描画し、バックエンドでRDKit substructure searchへ変換する。これにより検索構文エラーを避ける。
  • 対象：Reactant / Product / 両方を選択可能。
  • 個人利用・小規模Libraryを想定し、初版はSQLite内候補をRDKitで逐次照合する方式でよい。
  • 将来件数が増えた場合のみfingerprint index等を検討する。

  • Reaction SMILES（生成可能な場合）
  • 試薬・触媒・溶媒・添加剤等の情報
  • 加工条件・工程の自由記述
  • 一般自由記述メモ
  • 最新Validation結果とcoverage

Reaction SMILESを生成できないポリマー等では、その旨と利用可能な構造表現情報を明示し、コピー操作自体は可能とする。

11.2 構造式のコピー

  • アプリ内で常に構造式・反応式を描画表示する。
  • Word、PowerPoint、Excelへの貼り付けを主用途とする。
  • 「構造式をコピー」操作を提供する。
  • 実装優先順位は、可能であればSVG等のベクター表現を優先し、互換性確保のためPNG等のラスタ形式へのフォールバックを用意する。

11.3 外部からの戻し

AI等との議論結果から得た反応はReaction SMILESまたはRXNとしてImportし、Editor確認 → Validation → 登録の通常フローに戻す。

12. バックアップ・復元

  • アプリからSQLite DB全体を1ファイルとしてバックアップできる。
  • バックアップファイルからLibrary全体を復元できる。
  • 人間可読なJSON/CSV等へのexportは初版では不要。
  • 復元時は現在DBを上書きする前に明示確認する。
  • DBスキーマの将来変更に備え、スキーマバージョン管理の仕組みは内部的に用意する。

16. 品質・テスト要件

16.1 自動テスト

  • chemistry層はpytestで単体テストする。
  • 既知の正常反応、元素収支不一致、電荷不一致、未mapping、ポリマー、架橋局所構造等をfixture化する。
  • FastAPI endpointのintegration testを用意する。
  • FrontendはTypeScript typecheckと主要フローのUIテストを実施する。

16.2 重要エッジケース

  • explicit H / implicit H
  • formal charge
  • isotope
  • 芳香族結合
  • salt / 複数成分
  • condition componentの収支除外
  • dummy atom / wildcard
  • polymer S-group / SRU
  • Reaction SMILESを生成できない保存可能構造
  • 単一nを含むrepeat-unit validation

16.3 AIエージェント開発向けルール

  • 機能追加時に既存testを実行する。
  • Validationの判定条件をUIコードへ重複実装しない。
  • API契約はPydantic/OpenAPIを正とし、Frontend型と同期する。
  • 化学的妥当性と機械的Validationを混同しない。

18. 初版受入条件

  1. Editorで低分子反応を描画し、反応物・生成物・condition component・係数を設定できる。
  2. Reaction SMILESまたはRXNをImportし、Editorで確認・修正できる。
  3. Editor/Importの双方が同一Validationフローへ入る。
  4. FULL / REPEAT_UNIT / LOCAL / LIMITEDを自動判定できる。
  5. 低分子反応で元素・電荷収支、構造、atom mapping等を評価できる。
  6. 単純ホモポリマーで単一nを考慮したrepeat-unit validationができる。
  7. 架橋等をLOCALとして保存・局所Validationできる。
  8. Warningがあってもユーザー判断で登録でき、Warning理由を任意記録できる。
  9. 反応をLibraryへ保存し、編集・削除・個別再Validation・一括再Validationできる。
  10. Reaction SMILES完全一致時に重複Warningを表示できる。
  11. 試薬名、タグ、自由記述、Reactant/Product、部分構造で検索できる。
  12. AI用テキストを1操作でコピーできる。
  13. 構造式をWord / PowerPoint / Excelへ貼り付け可能な形でコピーできる。
  14. SQLite DB全体をアプリからバックアップ・復元できる。
初版の完成定義：「構造を入力・Importする → 機械的に検証できる範囲を自動判定する → ユーザーが結果を理解して登録判断する → 後から構造・メモ・Validation結果を検索・再利用できる」という一連のワークフローが成立していること。
